# Notes

## Pillar 1

- **Keep:** distroless `static:nonroot` with a `CGO_ENABLED=0` static binary. Image `devops-app` (`linux/amd64`) is **19.9 MB** uncompressed in `docker image ls` and 4.74 MB compressed, runs as `65532`, and has no shell.
- **Broke:** pulling `golang:1.27` stalled on the same layers from both Docker Hub and `mirror.gcr.io`, while `curl` fetched those layers at about 10 MB/s, so the network was fine and Docker Desktop's pull engine was stuck. **Fixed:** restarting Docker Desktop; the pull then took 21 s.
- **Checked the failure path on purpose:** a throwaway PR in my personal repo (closed, not merged) first broke `TestHealth`. `Test` failed and the single `Build & Push` job of the time was skipped. After the revert, the image built with `push: false` and nothing reached GHCR (`captures/step-1-pr-test-fail.png`, `captures/step-1-pr-build-no-push.png`). **Keep:** prove the gates with a deliberate failure instead of trusting the YAML.
- **Publish only what was tested:** I split `Build & Push` into `Build` (build once, `make smoke`, Trivy image scan, SBOM) and `Publish`, which pushes that same image only if its image ID matches, then signs it with keyless cosign and attests provenance and the SBOM. A parallel `Security` job adds gitleaks over the full history and `trivy fs`. The first push created the GHCR package as private; after I set it to Public, an anonymous manifest request for `:latest` returns `200`, so Pillar 2 needs no image-pull secret. **Keep:** a rebuild in the push job could ship bytes nobody scanned.
- **Keep:** each version pin lives in one place per tool (`go.mod` → `setup-go` via `go-version-file`; golangci-lint `v2.14.0` in the `Makefile` and `ci.yml`). `make lint` refuses to run on a different golangci-lint version, so local and CI lint results can't drift.

## Pillar 2

- **Sized limits by measuring, not guessing:** k6 with 100 VUs against one pod (`/api/work?ms=50`) pinned CPU at a 500m limit (throttled, ~1.6k rps, p95 74 ms). With a `1` CPU limit it peaked at ~560m and 15Mi (~1.75k rps, p95 62 ms, 0% failed), so the Deployment keeps `1` CPU / `128Mi`, about 2x CPU and 8x memory headroom for Pillar 3.
- **Rolling restart dropped requests until I added a `preStop` sleep:** a curl loop from a pod in the namespace (~8 req/s to `devops-app:8080/api/work`) saw the new `MESSAGE` after `kubectl rollout restart`, but 4, 1 and 2 requests failed in three runs (connection refused or a 2 s timeout), because the app closes its listener on `SIGTERM` before kube-proxy stops routing to the pod. With `lifecycle.preStop.sleep: 5s` (the default 30 s grace period still covers the app's 10 s drain), three runs had 0 failures, so the Deployment keeps it.
- **Self-healing and rollback worked as designed:** a deleted pod's replacement was `Ready` and the Deployment back to `2/2` in 6.6 s. A rollout to tag `does-not-exist` created one surge pod (25% of 2 replicas rounds to `maxSurge: 1`, `maxUnavailable: 0`) that cycled between `ErrImagePull` and `ImagePullBackOff`, while both old pods stayed ready and served all 496 requests in the window. `kubectl rollout undo` scaled the bad ReplicaSet to 0 and left the old one at `2/2` with the same pods. `kubectl diff -k` already returned 0 after the undo: `kubectl set image` never touched the `last-applied-configuration`, so it matched git throughout, and the undo restored the same template. The re-apply matters when the bad change came from `kubectl apply` itself.
- **Remote access goes through a LoadBalancer Service, not `kubectl port-forward`:** a `cloudflared` quick tunnel points at `localhost:8080`, which k3d maps to a new `LoadBalancer` Service `devops-app-lb` on port 8080 (not 80/443, which k3s's Traefik owns). It got `EXTERNAL-IP` `172.18.0.3`, and `curl localhost:8080/api/work` returns `200`. **Keep:** `port-forward` sends every connection to one pod and exits when that pod restarts, so a rollout would silently break the tunnel. The LoadBalancer path spreads traffic across both replicas and survives restarts. The extra Service is labelled `app.kubernetes.io/component: remote-access` so the Pillar 3 ServiceMonitor can exclude it and not scrape each pod twice.
